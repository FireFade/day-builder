# Технічний аудит Day Builder 1.0 Beta

**Дата:** 2026-11-02  
**Джерело:** вихідний код `day-builder-v1.0-beta.zip` і документація `README.md`, `CHANGELOG.md`, `docs/QA-v0.3.md`–`docs/QA-v1.0.md`, `docs/RELEASE-v1.0.md`, `docs/architecture.md`, `docs/product-plan.md`. Окремого експорту повного чату в архіві немає.  
**Межа висновку:** це аудит локального однокористувацького застосунку. Публічний GitHub-репозиторій містить вихідний код і не означає публікацію чи безпечне розгортання сервера.

## Короткий висновок

Day Builder має робочий вертикальний зріз для локального персонального планування. Backend, SQLite/SQLAlchemy, шість послідовних Alembic-міграцій, основний беззбірковий вебклієнт, імпорт календарів та автоматизовані backend-тести наявні. Після виправлення посилань видаленої активності повний backend-набір містить 68 тестів.

Beta ще не має підстав називатися production-ready для публічного сервісу. Немає автентифікації Day Builder і багатокористувацької ізоляції; живий OAuth та повний ручний регресійний цикл не перевірені. Планування використовує місцеві часи в межах однієї дати, без повної підтримки DST та подій через північ. Ці межі описані в архітектурі й release notes.

## Інвентаризація реалізації

| Функціональна зона | Фактичний стан |
|---|---|
| Активності, налаштування дня, харчування, фіксовані події, перегляд і застосування денного плану | Реалізовано в API та основному `web/`; правила валідуються на сервері |
| Планувальник | Реалізований детермінований bounded backtracking із 15-хвилинною гранулярністю, буферами, залежностями та попередженнями; це не оптимальний CP-SAT solver і не гарантує знаходження всіх можливих розкладів |
| Google Calendar / Microsoft Graph | OAuth із PKCE, зашифрований локальний vault і синхронізація реалізовані; тести використовують mock HTTP, живі облікові записи не перевірялися |
| Ручне редагування, закріплення, переміщення, Undo/Redo, експорт ICS | Реалізовано; регресійні тести є |
| Тиждень, аналітика, фокус, підсумки дня | Реалізовано в локальному UI та API; без серверних push-повідомлень |
| Inbox, цілі, звички, шаблони, календарна сітка, темна тема | Реалізовано у `web/` та API; покриті окремими backend-тестами |
| Офлайн | Кешується статична оболонка й останній перегляд у браузері; офлайн-редагування та черги синхронізації немає |
| `frontend/` React/TypeScript | Частковий прототип без паритету функцій; підтримуваний інтерфейс для beta — `web/` |
| Резервна копія | SQLite snapshot у ZIP без `.env` і ключа токенів; відновлення та повторне підключення потрібно перевірити вручну |

## Пріоритетні проблеми

### P1 — блокери публічного сервісу

1. **Немає входу, авторизації чи ізоляції користувачів.** Наявна конфігурація навмисно прив'язує сервер до loopback. Для особистого локального запуску це очікувана межа; до розміщення застосунку в Інтернеті потрібні автентифікація, контроль доступу на кожному маршруті, ізоляція даних і безпековий перегляд.
2. **Не пройдено live Google/Microsoft OAuth.** Моки не перевіряють redirect URI, згоду, refresh token, права акаунта, повторну авторизацію та стабільність синхронізації з реальним календарем. Потрібен ручний тест на резервній копії даних і реальному локальному Windows-запуску.

### P2 — обмеження коректності та готовності до випуску

3. **Часові зони й дні переходу на літній/зимовий час.** Планувальник працює з місцевими хвилинами одного дня; багатоденні події, DST fold/gap і події через північ не мають повного покриття.
4. **Немає наскрізного браузерного регресійного тесту з реальним backend.** Історична документація згадує mock UI smoke, але сценарії `DB1-01`–`DB1-22` залишені як ручні. Їх результати не можна позначати PASS за наявністю unit/API-тестів.
5. **Прототип React може ввести в оману як альтернативний UI.** Він не має паритету й не є рекомендованою точкою входу. До окремого рішення слід тестувати й підтримувати `web/`.
6. **Інтеграційний ризик між моделями.** У таблицях нових функцій частина ID-посилань не має обмежень зовнішніх ключів у БД. API-видалення активності тепер очищає Inbox і habit references без втрати самих записів; для прямих змін БД та інших залежностей потрібна подальша системна перевірка цілісності.

### P3 — інженерна підтримка

7. Діапазони Python-залежностей широкі, lock-файлу немає; поточний тестовий прогін показав deprecation warning у FastAPI/Starlette TestClient. Потрібні повторюване середовище CI та план оновлення залежностей.
8. Немає CI workflow для автоматичного запуску тестів, міграційної перевірки й статичного аналізу на кожному коміті.

## Виконані перевірки

- Backend: 68 pytest-тестів пройшли з `backend/` як робочою директорією. Базові 66 пройшли до зміни; два нові тести перевіряють видалення посиланої активності й збереження історичного блока.
- `node --check web/app.js` та `node --check web/sw.js` — PASS.
- Alembic має одну голову `0006`; synthetic SQLite upgrade `0005 → 0006` пройшов зі збереженням прикладу плану, активності, виконаного блока й ciphertext токена. Реальну базу користувача тут не використовували.
- Невиконано тут: UI UAT на 390/1100/1440 px, live OAuth, Docker запуск, відновлення бекапу та міграція копії реальної бази користувача.
- Є один deprecation warning від Starlette TestClient щодо використання httpx; функціональні тести проходять.

## План доведення до стабільного локального релізу

1. Зберегти базу, `.env` і `backend/.secrets/calendar.key` окремо; на тестовій копії перевірити Alembic `0005 → 0006`, кількість/вміст планів і збереження токенів.
2. Запустити повні backend-тести, перевірити межі валідації та вирішити deprecation попередження шляхом узгодженого оновлення тестового клієнта.
3. Виконати ручні сценарії `DB1-01`–`DB1-22`, включно з live Google OAuth і повторною синхронізацією; записати PASS/FAIL/BLOCKED із фактичними результатами.
4. Перевірити резервне копіювання й відновлення на копії; підтвердити, що `.env` і ключ не входять до архіву та не додаються в Git.
5. Прийняти продуктову межу локального режиму й явно позначати її в документації. Не виставляти локальний API у публічну мережу без окремої реалізації та аудиту безпеки.
6. Для майбутньої веб-публікації окремо розробити модель часу на UTC/IANA, DST/overnight тести, автентифікацію, CI, спостережуваність і контрольоване розгортання.

## Зауваження щодо відкритої публікації коду

Публічний GitHub-репозиторій можна використовувати як посилання на вихідний код та модульні тести у звіті лабораторної. Перед першим push перевірити, що в коміт не потрапили `.env`, локальна база, `.secrets/calendar.key`, access/refresh tokens або персональні календарні дані. GitHub commit hash у звіті лабораторної має вказувати саме на версію коду, яку аналізували.
